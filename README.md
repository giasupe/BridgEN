# BridgEN

2D RPG の会話を読み取り、日本語訳を画面に表示する Windows アプリです。

アプリ名・C#プロジェクト名・名前空間はBridgENに統一しています。

Cloudflare Workersの中継サーバー、招待トークンの発行、Windows用ZIP、GitHub Releasesの準備は[配布手順](docs/distribution.md)を参照してください。利用者向けの説明は[起動ガイド](docs/user-guide.md)にあります。

ディレクトリ構造、各ファイルの役割、画面取得から翻訳表示までの流れは[構造と処理の解説](docs/architecture.md)を参照してください。

## 最初の開発方針

- .NET 10 / WPF のデスクトップアプリ
- ゲーム窓の選択、固定範囲の会話枠検知、OCR、話者・文脈判断、翻訳、通知表示を段階ごとのモジュールに分ける
- それぞれは一つのアプリ内で動かし、画像ではなく必要な文字列や小さなデータだけを受け渡す
- 初期のクラウド翻訳先は Gemini 3.1 Flash-Lite
- 翻訳処理は ITranslationProvider を通して呼び出し、将来 OpenAI などへ差し替えられる形にする

## API キーと配布

API キーをソースコードや配布物に埋め込みません。初期の個人利用では利用者自身のキーを安全に設定する方式を検討し、配布時に開発者が費用をまとめて負担する場合はサーバー経由に切り替えます。

配布版は「翻訳の接続設定」で中継サーバーURLと利用者別の招待トークンを登録します。招待トークンはWindowsユーザーに紐付けて暗号化し、`%LOCALAPPDATA%\BridgEN\connection.json`に保存します。Gemini APIキーはCloudflare WorkerのSecretに置き、配布物には含めません。初回起動は中継サーバーモードです。

開発中に従来の直接接続を使う場合は、接続設定で「Geminiへ直接接続」を明示的に選び、Windows のユーザー環境変数 `GEMINI_API_KEY` または `GOOGLE_API_KEY` にキーを設定してください。キーの値を `run.bat`、ソースコード、GitHub に書かないでください。

## 現在の状態

対象ウィンドウとドラッグで選択した会話範囲を、Windows Graphics CaptureとWindows標準の英語OCR（en-US）で読み取ります。文章の確認中は最短250ms、確定後や文字がない場合は通常400ms間隔で処理します。通常間隔を800msから400msへ短縮して次の台詞を見つけるまでの待ちを減らしています。OCRが処理中の場合は重ねて実行せず、実際の間隔は処理時間とフレームの到着にも左右されます。対象ウィンドウが前面にある間だけ動作します。Z / Enterの監視は押下回数の表示に使い、OCRの開始条件にはまだ使っていません。

OCRは選択範囲全体を同じ方法で処理します。初回や必要な再確認時には、元画像、最大2倍のグレースケール・コントラスト調整、局所しきい値処理、全体しきい値処理を比較します。追加の3候補は独立した画像とOCRエンジンで最大2件ずつ並行処理します。論理プロセッサ数が4未満の環境では1件ずつに制限し、追加エンジンが使えない場合も従来のエンジンによる逐次処理へ戻します。候補の採点は従来と同じ順序で行い、タスクの終了順で採用結果を変えません。画像読み書きの中間コピーも削減しています。良い結果が得られた画像処理を選び、次の読み取りにも同じ画像処理を適用します。再確認の間だけ元画像へ戻すことはありません。再比較は最短約1.5秒間隔、正常な読み取りでも約6秒ごとに行います。走査線による孤立した1ピクセルの切れも補正します。

認識候補は文章の近さと連続した読み取りで確認し、同じ台詞の読み取りが揺れる場合は良い候補を保持します。空白を整えた実際の読み取りと採用文章が連続して完全一致し、各行に疑わしい文字がない場合は、少なくとも2回の一致と画像取得間隔250ms以上を条件に送信します。最初のOCR処理が終わった後から350msを数える方式を見直し、別々の画像の取得時刻を比較することで、初回のOCR処理中に過ぎた時間も確認時間に含めます。実際の送信時刻はフレーム到着とOCR完了に左右されます。一度でも採用文章と異なる読み取りがあった版や、疑わしい文字を含む文章は従来どおり採用後約1秒確認します。確定した版は保持したOCR候補の揺れだけでは未確定に戻しません。別の文章や文字送りで版が変わると確認をやり直します。背景の画素が変わっただけでは翻訳待ちをリセットしません。

確定後は文字列だけをGemini 3.1 Flash-Liteの `streamGenerateContent?alt=sse` へ送ります。自然なRPGの日本語と、確度の高いOCR崩れだけを補正する指示を短くまとめ、推論量は従来の `minimal` を維持します。受信した日本語を結果欄とオーバーレイへ逐次表示し、初回は即座に、その後は最短約50ms間隔にまとめて表示を更新します。通常のOCR確認イベントで受信途中の訳が英語に戻ることはありません。話者や会話履歴を渡す窓口はありますが、アプリからの接続は今後の課題です。

ストリーミングは全文の生成完了を待たずに表示を始めるための変更で、Google側の混雑や通信の往復時間まで短縮できる保証はありません。SSEの文字列は分割位置の空白・改行を保持して連結し、思考用のテキストは表示しません。正常な終了理由 `STOP` を確認した訳だけを完成結果として保存します。受信切断、出力上限、APIエラー、タイムアウトでは途中の訳を完成扱いせず、エラー時には英文へ戻します。45秒の期限はヘッダー受信だけでなく本文の受信にも適用します。

### 接続準備と翻訳結果の再利用

APIキーが設定されていれば「OCRを開始」を押した時点で、APIホストへの認証不要のHEADリクエストを先行させます。DNS・TLS接続の準備を実際の文章送信より前に始めるためで、キーや本文は送信せず、生成APIも呼びません。接続準備の失敗は翻訳を止めず、最長5秒で打ち切ります。重複した準備は2分間抑えます。翻訳は共有HttpClientの接続プールを使い、HTTP/2を優先し、対応しない環境では従来のHTTPへ戻します。接続が既に再利用されている場合は、この準備による大きな短縮は見込めません。

完成済みの訳は直前の1件から最大128件のメモリ内LRUキャッシュへ拡張しました。安定確認を通過した英文が完全一致すれば、直前とは異なる台詞を挟んでもAPIを呼ばずに再利用します。空白以外の表現や単語の違いを曖昧比較して流用することはありません。対象ウィンドウ・読み取り範囲を変えると消去し、アプリ終了後にも保存しません。本文と訳の合計が16,384文字を超える結果は保存対象から外します。失敗・中断・受信途中の訳は保存しません。将来、話者や会話履歴を翻訳条件に接続する場合は、その情報もキャッシュのキーに追加する必要があります。

英文は確認欄に表示し、翻訳された日本語はゲーム画面上部に追従するクリック透過オーバーレイへ表示します。翻訳待ちやAPIエラー時は英文を表示します。新しい文章に切り替わったと判断したときは古い翻訳をキャンセルし、古い結果の表示を防ぎます。APIエラーで同じ文章を読み取るたびに再送信することはありません。再試行する場合はOCRを停止して再開してください。

英語OCRにはWindowsの英語（米国）OCR言語機能が必要です。ウィンドウキャプチャはWindows 10バージョン1903以降が必要です。画像はLLM/APIへ送信しません。

## クライアントの結果表示と処理時間

クライアントには「OCR結果」と「翻訳結果」を別々に表示します。対象や読み取り範囲を変更した場合、新しい英文を採用した場合は、前の日本語訳を消して対応関係を保ちます。OCRを停止したりゲームからクライアントへ切り替えたりしても、直前の結果と計測値を確認できます。

「処理時間」は `Stopwatch` で実測したミリ秒です。

- 最新のOCR処理: 画面取得・CPUへのコピー、範囲切り出し、画像補正・特徴抽出、OCR認識、単語座標からの行の組み直し、補正比較・再認識、品質・安定判定、OCR処理全体。
- 現在の文章の翻訳処理: その文章の初回OCR処理（補正比較を含む）、最初のOCR結果をクライアントが受け取ってから送信するまでの文章確認・安定待ち、API初回テキスト、API受信全体、表示更新の累計、画像取得から最初の訳の表示開始まで、画像取得から翻訳完了まで。左側の「最新のOCR処理」が次のフレームで更新されても、右側には初回の処理時間を保持します。

安定待ちには次のOCRによる確認や読み取り間隔も含みます。API初回テキストは翻訳リクエスト開始から最初の空白以外の日本語を受信するまでで、HTTPヘッダーの受信時間ではありません。API受信全体には通信、モデルの生成時間、逐次表示の更新待ちを含み、サーバー側の生成時間だけを分離した値ではありません。表示更新はWPFへの内容設定までで、モニターへの描画完了は含みません。取得からの時間は採用した文章の版を最初に取得したフレームから計測し、そのフレームを取得する前の待ち時間は含みません。左側は最新フレーム、右側はその文章の翻訳なので、各行の単純な足し算は合計と一致しません。

安定待ち・API応答待ち・受信中は約250msごとに経過時間を更新します。未計測は「—」、そのフレームで実行しなかった補正比較などは「省略」、保存済みの訳を使った場合は「再利用」と表示します。中断・失敗した翻訳には完了までの合計を表示せず、古いリクエストが後から終了しても次の翻訳の計測値を上書きしません。

## 認識上の課題と対策方針

現在確認している主な課題は、文章全体をまったく認識できないことだけではなく、文章の一部の単語が丸ごと抜けることです。残った英文が自然に見える場合は、文字列の読みやすさだけでは抜けを検知しにくく、Geminiへ文字列だけを渡しても元画像にない単語を確実には復元できません。

次の改善では、OCRが返す単語の位置情報から、隣の単語との間隔が不自然に広い箇所を探します。疑わしい行を周辺文字も含めて切り出し、拡大や別の画像補正で再認識して候補を比較します。英文の自然さだけで補完を決めず、画像上に文字がありそうなのにOCR結果が欠けている場合を優先して再確認します。翻訳APIには上記の安定確認を通過した文章だけを送信します。画像をAPIへ送らない方針は維持します。

## OCR結果の揺れへの対策

前回の輪郭比較では、明るい背景の動きでも画面変更として候補と翻訳待ちをリセットすることがありました。現在は画像差分を補助情報にとどめ、認識した文章の連続性と組み合わせます。空白や句読点の揺れを比較用に正規化し、近い文章の読み取りを同じ台詞の候補として扱います。翻訳に送る文章は実際の認識候補から選び、異なる読み取りの単語をつぎはぎして作ることはありません。

別の台詞や文字送りによる文章の伸びを検出すると安定待ちをやり直します。小さな単語変更は、変化した画面で同じ新しい読み取りが連続したときに切り替えます。そのため点数の低い次の台詞にも追従できます。長い単語や辞書にない単語という理由だけで減点する処理も見直しています。類似性と画像比較はいずれも推定のため、任意のゲームで誤認識をなくせる保証はありません。

診断用に `%LOCALAPPDATA%\BridgEN\logs\ocr-diagnostics.jsonl` へ時刻、画像処理の種類、画面差分の有無、採用理由、文字数、安定時間を記録します。OCR本文、画像、APIキーは記録しません。ファイルは約1MBで切り替え、前回分を1ファイルだけ保持します。保存できない場合もOCR自体は継続します。

参考調査として、[OwOCRの文章・重複処理](https://github.com/AuroraWright/owocr)と[Game Live Translatorの文字単位の合流処理](https://github.com/yuntoxic/game-live-translator)を確認しました。これらのコードは取り込んでいません。

### 行の復元

Windows OCRが返すまとまりを、そのまま画面上の1行として扱いません。認識された全単語の座標を取り出し、上下の重なりと高さから同じ行に属する単語をまとめ、上から下・各行の左から右の順に並べ直します。行の位置には中央値を使い、大きな括弧や小さい文字で隣の行へずれにくくしています。行数を3などに固定する処理ではありません。キーボード記法の `[]` と `/` も文字の採点で通常の記号として扱います。

添付された操作説明の画像（`tests/BridgEN.Ocr.WindowsSmoke/Fixtures/tutorial-controls.png`）では、強いコントラスト補正後にOCRが8個のまとまりを返す問題を再現しました。座標から組み直した結果は次の3行です。

```text
Hold [Arrow keys] to move
Hold [Shift] to run
Tap [Z/Space] to Investigate or talk
```

この行復元を全画像補正の候補に共通で適用し、その後に候補採点、安定判定、翻訳へ進みます。診断ログにも、OCRの元のまとまり数、座標で組み直した行数、候補と表示文章の行数を記録します。座標があってもOCR自体が読み落とした単語を復元できるとは限りません。

### 回帰確認

`dotnet run --project tests/BridgEN.Ocr.Regression/BridgEN.Ocr.Regression.csproj`

`dotnet run --project tests/BridgEN.Ocr.WindowsSmoke/BridgEN.Ocr.WindowsSmoke.csproj`

Windowsのen-US OCRと実際の画像前処理を使う確認です。WPFで生成した英語の会話画像に走査線と移動する明るい背景を重ね、継続した読み取りの安定と、次の台詞への切り替えを検証します。ネットワークやAPIキーは使いません。添付された実ゲームの操作説明画像でも、全4種類の画像処理を比較し、最良の候補が正しい3行になることを確認します。起動中ゲームからの連続キャプチャ全体を検証した結果ではありません。
